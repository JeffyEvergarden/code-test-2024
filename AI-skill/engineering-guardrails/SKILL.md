# Engineering Guardrails

在执行代码生成、改造、重构、修复问题时，必须遵循下面的交付规范。

## 适用场景

- 用户要求你编写、修改、重构代码
- 需求涉及 TypeScript 或前端工程规范
- 需求包含复杂逻辑调整、删除旧逻辑、跨文件联动
- 用户要求参考现有代码实现，并说明改动点

## 强制要求

### 1. AI 生成的代码必须补充关键注释

- 只在关键逻辑添加注释，不要给显而易见的语句写注释
- 注释应覆盖这些场景：
  - 复杂分支判断
  - 不直观的数据流或状态流转
  - 特殊边界条件
  - 兼容性处理
  - 替换旧逻辑时的设计取舍
- 注释目标是帮助人快速理解“为什么这样写”，而不是重复“这行代码做了什么”

### 2. 代码完成后必须核验 TypeScript 与 ESLint

- 先检查项目中实际存在的校验方式，例如 `package.json`、`eslint` 配置文件、`tsconfig.json`
- 必须运行项目内已有的 TypeScript 校验命令与 ESLint 命令
- 如果项目没有现成的 ESLint 或 TypeScript 校验命令：
  - 先查找仓库中是否存在可直接运行的替代方式
  - 如果仍然不存在，明确说明“无法完成该项核验”的原因
  - 绝不能在未执行的情况下声称已经通过校验
- 最终回复中必须写明：
  - 执行了哪些校验命令
  - 校验是否通过
  - 如果未执行，缺少什么配置或命令

### 3. 遇到复杂需求改动必须生成一份 Markdown 文件

满足任一条件即可视为复杂需求：

- 涉及多个文件或多个模块联动
- 涉及核心业务逻辑替换
- 需要删除、废弃、绕过原有实现
- 改动后需要额外说明影响范围、兼容性或迁移方式

复杂需求下，必须新增一份 Markdown 说明文件。优先放在仓库已有的文档目录；如果没有现成目录，再在合适位置创建。

Markdown 文件至少包含以下内容：

- 需求背景
- 涉及文件
- 逻辑变动点
- 删除了哪些旧逻辑
- 为什么删除这些逻辑
- 新方案相对旧方案的收益与影响
- 已完成的校验项

### 4. 参考现有代码时必须标注逻辑变动部分

- 如果用户要求“参考已有代码”实现新逻辑，必须明确指出：
  - 复用了哪部分思路
  - 改动了哪部分逻辑
  - 删除了哪部分逻辑
  - 为什么删除或替换
- 在最终回复和复杂需求的 Markdown 文件中，都要单独列出“逻辑变动”与“删除原因”
- 对于删除逻辑，不允许只写“已优化”或“已简化”，必须写出真实原因，例如：
  - 重复职责
  - 分支永远不会命中
  - 与新数据结构不兼容
  - 会引入额外副作用
  - 被统一流程替代

## 建议执行流程

1. 先阅读用户提到的文件和相关上下文
2. 按现有代码风格实现改动
3. 在关键位置补充必要注释
4. 如果属于复杂需求，同步生成 Markdown 说明文件
5. 运行 TypeScript 与 ESLint 校验
6. 汇总改动点、删除逻辑原因、校验结果后再回复用户

## 最终回复模板

最终回复至少覆盖以下内容：

- 修改了哪些文件
- 哪些位置是关键逻辑改动
- 哪些旧逻辑被删除
- 删除原因是什么
- 添加了哪些关键注释
- 执行了哪些 TypeScript / ESLint 校验
- 如果生成了 Markdown 文件，文件路径是什么

## 示例表述

- 逻辑变动：将原先分散在多个分支中的状态收敛到统一入口，减少重复判断
- 删除原因：移除了旧的兜底分支，因为新数据结构下该分支不再可能命中，保留会增加维护成本并造成误导
- 校验结果：已执行 TypeScript 与 ESLint 校验，最终无报错后再交付
